# G1R20 Fix6（2026-10-18）

G1R20 Fix5 をもとに、Issue [#29](https://github.com/tak063495-prog/excel-vba-rpfem/issues/29) のうち **P10A の GAP 2% 未達** を解消した版です。
方針は **精度確保が先、速度改善はその次** です。同じマシンで「速くなり、しかも GAP 2% 以内を保つ」と測定で確かめたものだけを「速度改善」と呼びます。確かめていないものは「候補」として分けて書きます。

**P06N/P06A は Fix6 では解決していません**（未対応・別PCでの検証待ち）。理由と今後の方針は下の「P06 について」を見てください。

DLL は Fix4・Fix5 と同じです（`rpfem_native_x64.dll`、SHA256 `66da1a21be43cd2b3a3bfbaa9d13aad5fb1fd1960e1bf2507cc4e1cfa9ebe70b`）。
配布ブック：`delivery/RPFEM_20261018_G1R20_Fix6.xlsm`（SHA256 `bd1eee7cad7534883aa8e14cd1530a5cd18cdc76d8ddfe8ff1fdb8b605f8289e`）。保存時の設定は Fix5 と同じ2%標準プリセット（`RPX_Speed2pctPreset`）です。

## 原因（P10A）

P10A の上界が 582 要素の 2.04794 から下がらなかったのは、メッシュや精度の限界が原因ではありませんでした。**HSD の1回あたりの時間上限（300秒）の判定の順序** が原因です。

- accuracy_2（790 要素）の上界は、まず conic を試して失敗し（約88秒）、HSD で救済します。この HSD は 36〜37 反復で収束圏にありました（残差 約1e-11、gap 約5e-8）。そこへ 300 秒の上限が来ました。
- Fix5 までは、反復の先頭で **収束判定より先に時間を確認** していました。このため、収束した反復も判定前に捨てられて `HSD_SOLVE_BUDGET_EXCEEDED` になり、細分化がそこで止まっていました。
- 下界（4018 要素の扇形細分、2.00606）は問題ありませんでした。

## 修正内容（`RPX_Solve.bas` のみ）

1. 時間上限の確認を、その反復の OPTIMAL 判定・証明書判定の **後** に移しました。
2. 時間上限に達した時点で、反復がすでに終盤にある場合に限り、上限の 1.5 倍まで続けられるようにしました（新設定 `HSD_ENDGAME_GRACE`、既定 0.5）。終盤の条件は、スケール済み主残差 < 1e-9、双対残差 < 1e-8、gap < 1e-6×(1+|目的値|) です。ログには `hsd_budget_endgame_grace` が残ります。終盤でなければ従来どおり打ち切り、`hsd_budget` に `endgame=False` を記録します。
3. 合格の基準（OPTIMAL の許容値、候補の原物理監査、根幅、GAP 2%）は **一切変えていません**。

### 時間について
- **P10A は Fix5 より約 935 秒遅くなりました**（1686 → 2622 秒）。Fix5 は途中で止まって未達だったので短かっただけで、Fix6 は 2% に届くまで計算しています。遅くなった主な理由は次の2つです。
  - accuracy_3（1185 要素）の上界：上限に達した時点で終盤ではなかったため（25反復、主残差 4.9e-7）打ち切りになりました。約440秒が結果に使われていません。
  - 最後の own_q8 の確認：上界側の再利用が条件不一致（`not_certified_same_mesh_q`）で使えず、790 要素を約425秒かけて解き直しました（Fsは同じ）。
- D05A・P02A・P05A では HSD の時間上限に一度も達していません。変更部分は実行されておらず、Fs は Fix5 と一致しています。時間の差は同じ経路での実行ごとのばらつきです（D05A は 188→245 秒と差が大きめですが、計算内容は同じです）。
- Fix6 には **速度改善はありません**。

### 速度の候補（未検証）
1. own_q8 上界の再利用が断られる条件を特定・修正する（P10A で約 −425 秒の見込み）。
2. 1回の求解が上限に収まらないと見込まれる精度ラウンド（反復あたり秒数×約38回 > 上限）は、始める前に打ち切る（P10A で約 −440 秒の見込み）。
3. 上界の conic を、同じモデルで一度失敗したら省いて HSD から始める（毎段階 40〜90 秒）。
4. band_refine と final が同じメッシュのときは、final で解き直さない（P10A で約 −230 秒の見込み）。

## P06 について（未対応）

Triela の Fix4 ログと [PR #30](https://github.com/tak063495-prog/excel-vba-rpfem/pull/30) の Python 証拠から、次のように見ています。
- P06N/P06A の GAP 未達の主因は **上界メッシュ** です。通常の細分化では上界の下がり方が非常に遅く、P06N は 1290 要素で 0.845 です（Python の 2% 対は 0.690）。
- Python で 2% に届いた対は、上界 8739 要素（辺 flip＋方向性細分）、下界 5966 要素（応力・角度の扇形細分）という、狙って作ったメッシュです。VBA の通常経路にはこれに当たる作り方がありません。
- P06 で上限に達した求解は P06N で 19 回、P06A で 27 回あり、そのうち終盤だったのは各 4 回だけです。Fix6 の延長は P06 にはほとんど効かないと見込んでいます。
- 次の版（Fix7）で、メッシュの作り方と、5000〜9000 要素の求解の扱いを検討します。P06N/P06A の VBA 実行は別PCで行います。
